## Product Interaction

### DevInspector 默认采用组件模式，元素样式仅服务普通对象

决定：

- 当选中对象可识别为组件根节点或 UI primitive 时，Inspector 默认进入“组件模式”。
- 组件模式优先展示组件名称、相同元素数量、状态信息、真实变体、可编辑内容插槽、子组件入口和面向 AI 的定位/任务动作。
- 组件模式的可编辑项通过 `Component Capability Registry` 维护：识别、相同元素规则、可编辑白名单、子组件入口和外部布局分开描述。
- 面板内只保留一个实底主按钮：默认是底部 `发送给AI`；选中态、分段控件和展开入口不使用实底主按钮样式。
- 组件识别成功后，不默认展示文字、容器、阴影、间距等细粒度 DOM 样式控制；组件内部只开放 capability 声明的变体、状态、内容插槽或子组件入口。
- 普通 DOM / 未识别对象仍可展示文字、容器、布局、阴影、间距等元素级样式能力。
- 相同元素分组按语义区分：业务组件按去状态后的业务类名分组；通用 primitive 按基础类分组，例如 `svg.lucide` 统一按 `.lucide` 分组。
- 组件命名分离为三层：源码真实 selector、Inspector 归一化展示名、组件属性。
- Inspector 展示名优先使用“类型-对象”，例如 `.task-card` 展示为 `card-task`；变体类不进入组件名，例如 `.ghost-button` 展示为 `button`，ghost 归入 `variant`。
- 组件卡片内只展示真实组件变体 / 属性；Card 的 `floating` 必须对应 `.task-card--floating` 这类真实变体，而不是临时追加 `box-shadow`。
- Card 这类组合组件可以开放内容插槽，例如标题和说明文；内容插槽默认只作用当前组件实例；状态标签等嵌套对象作为子组件入口展示，点击后进入子组件自己的 capability 面板。
- 组件作为页面里的整体时，可以在组件卡片外提供“外部布局”，用于位置和尺寸调整。
- 默认命名规则作为 DevInspector 推荐规范，同时预留外部 naming adapter，让其他项目可以导入自己的组件命名方式。

放弃：

- 不再默认把所有选中 DOM 元素都当成可自由修改对象。
- 不再在组件根节点默认暴露全部样式控制项。
- 不再把组件级调整和元素级调试混在同一默认面板里。
- 不再把组件内部所有文本都当作可编辑文本；只有组件定义开放的内容插槽可以直接改。
- 不再用紫色实底同时表达“当前选中值”和“主流程动作”。

原因：

- 用户选中组件时，真实意图通常是调整组件语义、变体、状态或提交给 AI 定位源码，而不是手动覆盖每个 CSS 属性。
- 默认暴露所有样式项会误导用户直接改 DOM 细节，增加破坏组件约束和设计 token 体系的风险。
- 图标尺寸、按钮 variant、卡片容器等调整更接近组件/primitive 级规则，应先按相同元素或组件定义处理。
- 元素级编辑仍然有调试价值，但应优先服务于普通 DOM / 未识别对象，避免在组件模式里误导用户绕过组件封装。
- 组件内部内容需要区分“可编辑内容”和“嵌套子组件”。例如 Card 标题、说明文可以作为当前实例的内容插槽改；“进行中”这类状态标签应先作为 `badge-status` 子组件被选中，再通过 Badge 的状态 / 色调能力控制。
- 主按钮只表达提交/继续主流程；选中态只表达当前值，两者视觉语义必须区分。
- 插件面向外部项目时，不能要求所有人改成 DevInspector 的源码 class；需要把“推荐规范”和“可导入识别规则”分开。
- 组件区里出现密度、阴影、容器这类样式词，会让用户误以为可以直接改组件封装，应回到真实变体；普通 DOM 才进入元素样式模块。

影响：

- 后续 UI 实现应保持“组件模式 / 普通元素样式”的分层。
- “相同元素”计数和批量作用范围应优先遵守组件语义，而不是只看单个具体 DOM class。
- `发送给AI` 的任务文本应优先输出组件名、选择器、作用范围和定位提示，帮助 AI 修改源码而不是手改 `dist`。
- 组件模式下的可编辑项应逐步改为白名单：例如 Button 可处理文案、variant、尺寸 token 和状态建议；Icon 可处理尺寸和颜色；Card 处理真实变体、标题、说明文和子组件入口。
- 新增组件类型时，应先登记 capability，再决定是否暴露组件属性；不要直接在默认面板里追加散乱样式控件。
- 后续新增控件时，选中态应使用浅底、描边、字色或标记，不使用与主按钮相同的实底反白样式。
- Inspector 的选中高亮不能覆盖组件自身阴影，否则无法验证 `floating` 等真实变体效果。
- 后续组件识别应抽出可配置 naming adapter：内置 DevInspector 默认规则，同时支持从项目配置、组件库规范或设计系统导入映射。
- `发送给AI` 的元素字段应使用 Inspector 展示名，真实 selector 单独输出，避免把源码 class 当成组件语义。
- 当前阶段不实现外部 adapter 导入或 workspace-aware 源码扫描，只把 L0-L3 识别方向归档到 `docs/PRODUCT_PLAN.md`。

## Design System

### 普通元素样式面板采用方案 F：微型工具条

决定：

- 普通 DOM / 未识别对象的样式面板采用 `方案 F：微型工具条` 作为当前密度方向。
- 文字属性、布局、阴影、间距优先压成浅底紧凑行，空值状态只显示标题和 `+` 添加入口。
- 阴影采用 H 合并形态：选择器即摘要，预览方块、token / 自定义名和具体值都合在同一个选择器里。
- 展开后仍保留 token、自定义、数值输入、步进、live apply 和本次修改记录，不用“紧凑”换掉已有能力。

放弃：

- 不再默认使用多张大卡片展示阴影、间距、布局。
- 不再在 `无 / 0 / none` 状态展示完整下拉和值说明。
- 不再把阴影的 token / 自定义名同时放在选择器和右侧摘要里重复展示。

原因：

- 用户高频操作是快速查看和微调当前属性，大卡片会把简单状态放大成噪音。
- 阴影和间距在空值时没有真实参数需要展示，直接提供添加入口更符合操作意图。
- DevInspector 是辅助定位和提议修改的工具，面板应优先让用户快速读懂当前值和进入下一步。

影响：

- 后续新增普通元素样式模块时，默认先按微型工具条设计；只有进入自定义或复杂参数时再展开。
- 文档和实现都必须保留“紧凑不丢能力”的约束。

## AI Workflow

### 组件创建先收口为普通元素抽屉

决定：

- `组件创建` 不并入普通样式调参能力，但第一版仍内置在 `@lijinmei-810/dev-inspector`，不要求用户额外安装组件制作 npm 包。
- 代码边界复用内部模块 `packages/dev-inspector/src/plugins/component-maker.ts`，由 DevInspector 收集选中上下文，组件创建能力负责格式化规格和 AI 任务文本。
- 组件创建 MVP 只支持“把当前普通元素创建为组件规格”：普通元素底部显示 `创建组件`，点击后打开轻量抽屉，先确认归类，再生成组件名，并确认使用场景和可改内容。
- `使用场景` 用一句自动生成的产品语言解释组件为什么存在；`可改内容` 用自动识别的勾选列表确认未来 props / 可配置字段，固定封装或子组件作为只读内容展示，不在 UI 中使用“槽位”主文案。
- `归类` 定义为当前对象职责路径，而不是 token 或已有组件实例；归类字段采用可搜索下拉，但只展示当前元素同一大类内的内置职责，例如 `文本 / 标题 / 页面标题`，避免把全量组件库塞进归类选择。
- 同一归类已有组件时，不静默覆盖或重复创建；抽屉必须展示 `已有同类`，让用户明确选择复用已有组件或新建同类组件。
- 抽屉确认后写入 `本次修改内容` 的 `组件规格` 记录，最后统一通过 `发送给AI` 生成任务文本。
- 已识别组件不显示 `创建组件` 入口；组件模式继续处理真实变体、可编辑内容、子组件入口和外部布局。
- 组件名建议避免 `h1`、`div` 这类通用标签名，标题类元素优先生成 `page-title`、`section-title` 等语义名。
- `同样式` 不再作为独立入口；样式复用统一由 `复制样式` 进入 `本次修改内容`，最后通过 `发送给AI` 发出。
- `组件创建` 不常驻在主样式模块流中，改由底部 `创建组件` 次级按钮打开抽屉；这样保留当前选中上下文和统一发送链路，同时避免普通样式调参页面被低频组件建模信息挤满。
- 内置能力不自动创建组件文件、不批量改源码、不绕过现有样式面板。

放弃：

- 不在第一版直接拆独立 npm 插件包。
- 不在当前版本做组件库浏览、加入已有组件、多变体批量生成或基于当前组件生成新组件。
- 不新增独立 `同样式` 按钮或第二套样式同步任务流。
- 不把组件制作做成“请 AI 自己判断并生成”的单一黑盒按钮。

原因：

- 组件创建的用户心智是“设计组件契约”，不是“调当前元素样式”；如果混进样式面板，会把高频样式调整和低频组件沉淀搅在一起。
- 组件创建仍需要复用 Inspector 的选中、高亮、selector、token、本次修改内容和 AI 发送链路，太早拆 npm 会提高外部安装成本。
- 当前用户确认的近期目标是“普通元素变成组件”，不是组件库设计器；收口到单一抽屉能降低误操作和解释成本。
- “创建变体”需要改源码中的 props、类型、token 映射和样式表；当前没有真实组件库上下文时容易让用户看到假的预览，因此先不做。
- `h1`、`div` 等标签名不是组件命名，直接写进组件规格会误导 AI；语义命名更利于后续源码落地。
- 规格草稿进入修改篮后，用户能统一删除、审阅和发送；这比立即生成源码更符合当前“AI 落地、人先确认”的协作模式。
- 组件创建需要 AI 理解源码结构、组件边界和 token 体系，直接自动改源码风险高。
- `复制样式` 已经会把样式变化写入 `本次修改内容`，再统一交给 `发送给AI`；独立 `同样式` 会造成用户心智和实现路径重复。
- 当前 DevInspector 的核心价值是帮助 AI 定位页面对象、收敛任务文本和避免手改 `dist`；先把任务生成跑通，比先做自动化更稳。

影响：

- 组件创建 UI 必须保持次级层级，不抢 `发送给AI` 的主按钮。
- 组件创建后续扩展前，必须先验证当前“创建组件抽屉 -> 修改篮 -> 发送给 AI”链路稳定；不要重新引入多动作大表单。
- 后续若要独立分发组件制作插件包，应先验证组件规格草稿和任务文本在外部项目里能稳定引导 AI 找到源码。
